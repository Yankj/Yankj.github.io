# Agent 数据库设计：标量、向量、JSONB 三种数据形态

传统数据库设计只需要考虑标量字段：`id`、`title`、`score`、`created_at`。但在 Agent 业务中，你还需要存 LLM 生成的高维嵌套 JSON 和 Embedding 向量。一张表要同时容纳三种完全不同的数据形态。

## 痛点：传统 DB 设计 vs AI 业务 DB 设计

传统 CRUD 应用的数据表设计通常是：

```
users: id, name, email, age, created_at
notes: id, user_id, title, content, created_at
```

全是标量——整数、字符串、时间戳。数据库可以直接 `WHERE age > 18` 做精确查询。

但 Agent 业务的数据长这样：

- **LLM 生成的嵌套结构**：考题数组 `[{ id, question, options: [4个选项], correctAnswerIndex, explanation }]`——字段可变、层级嵌套
- **Embedding 向量**：1536 维浮点数组 `[0.0123, -0.1542, ..., 0.8901]`——用于语义相似度检索
- **盲区列表**：`['向量计算', 'Rerank', 'pgvector']`——简单的字符串数组

这些数据塞不进传统的 `varchar` 或 `integer` 字段。

## 三种数据形态对比

Agent / AI 业务中，数据库设计需要同时兼顾三种形态的数据：

| 数据形态 | 特点 | PG 存储方案 | 典型示例 |
|---------|------|-----------|---------|
| **标量与关系数据** | 固定字段、强类型、可 SQL 精确查询 | `text` / `integer` / `pgEnum` | `id`, `user_id`, `status` |
| **非结构化语义向量** | 高维浮点数组，用于相似度检索 | `vector(1536)` (pgvector) | `embedding` |
| **半结构化/高维 JSON** | 嵌套结构、字段可变、需灵活存储 | `jsonb` + Zod 强类型映射 | `quiz_questions`, `key_gaps` |

关键认知：传统数据库设计只考虑标量；AI 业务还需要向量字段（语义检索）和 jsonb 字段（LLM 生成的复杂嵌套结构）。

## PG 类型映射表（AI 业务视角）

PostgreSQL 提供了丰富的原生数据类型，Agent 业务中最常用的 6 个：

| 业务需求 | PG 字段类型 | Drizzle 语法 | 适用场景 |
|---------|-----------|-----------|---------|
| 基础文本 | `text` | `text('topic')` | 主题名、问题描述 |
| 分数/百分比 | `integer` | `integer('mastery_score')` | 0-100 整数 |
| 枚举类型 | `pgEnum` | `pgEnum('severity', ['low','medium','high'])` | 限制只存指定选项 |
| 简单字符串数组 | `text[]` | `text('key_gaps').array()` | 盲区列表 `['向量计算','Rerank']` |
| 复杂嵌套 JSON | `jsonb` | `jsonb('quiz_questions').$type<QuizQuestion[]>()` | 多层嵌套结构，支持 JSON 查询 |
| 向量数据 | `vector(1536)` | `vector('embedding', { dimensions: 1536 })` | Embedding 向量存储 |

> 各类型的详细定义和差异，详见 [Agent 全栈技术栈：PostgreSQL 数据类型详解](../concept/agent/2026-08-09_概念_Agent全栈技术栈.md)。

### jsonb vs json：为什么选 jsonb

PostgreSQL 提供两种 JSON 类型，差别不小：

| | `json` | `jsonb` |
|--|---------|---------|
| 存储方式 | 原始文本 | 二进制解析格式 |
| 保留输入顺序 | 是 | 否 |
| 支持索引 | 不支持 | 支持 GIN 索引 |
| 查询性能 | 每次解析 | 预解析，快 |
| 适用场景 | 仅记录原始 JSON | **Agent 业务首选** |

Agent 业务几乎总是用 `jsonb`——它支持 `@>`（包含）和 `?`（键存在）等 JSON 查询操作符，还能建 GIN 索引加速。

## Drizzle Schema 示例：study_diagnoses 表

以"个人学习助手"为例，Agent 评估用户笔记后生成诊断结果（掌握度评分、盲区列表、考题），需要持久化存入数据库：

```typescript
// 示意代码，展示关键类型用法
import { pgTable, uuid, text, integer, jsonb, timestamp, pgEnum } from 'drizzle-orm/pg-core';

// 枚举：限制严重程度只能是这三个值
const severityEnum = pgEnum('severity', ['low', 'medium', 'high']);

const studyDiagnoses = pgTable('study_diagnoses', {
  id: uuid('id').defaultRandom().primaryKey(),
  topic: text('topic').notNull(),                    // 标量：主题名
  masteryScore: integer('mastery_score').notNull(),  // 标量：0-100 分
  keyGaps: text('key_gaps').array().notNull(),       // 数组：盲区列表
  severity: severityEnum('severity').default('medium'), // 枚举：严重程度

  // jsonb：复杂嵌套的考题数组，搭配 TS 泛型做类型约束
  quizQuestions: jsonb('quiz_questions').$type<Array<{
    id: string;
    question: string;
    options: string[];              // 4 个选项
    correctAnswerIndex: number;     // 0-3
    explanation: string;
  }>>().notNull(),

  createdAt: timestamp('created_at').defaultNow().notNull(),
});
```

这张表的设计思路：

1. **标量字段**（`topic`, `masteryScore`）：用 `text` 和 `integer`，可以直接 `WHERE mastery_score > 80` 精确查询
2. **枚举字段**（`severity`）：用 `pgEnum`，数据库层限制只能存 `'low'` / `'medium'` / `'high'`，脏数据直接拒绝
3. **数组字段**（`keyGaps`）：用 `text[]`，PG 原生支持数组类型，可以 `'向量计算' = ANY(key_gaps)` 查询
4. **嵌套 JSON 字段**（`quizQuestions`）：用 `jsonb` + `.$type<T>()` 泛型，既享受 JSON 的灵活性，又有 TypeScript 类型安全

## 认知升级

记住这三句话：

> **简单字段存 SQL 标量。**
> **向量存 pgvector。**
> **复杂嵌套结构存 JSONB + Zod 强类型映射。**

这是从"前端/传统思路"向"Agent 全栈数据架构思路"演进的核心认知。传统数据库设计只考虑"字段是什么类型"；AI 业务数据库设计还要考虑"数据是什么形态"——标量、向量还是半结构化 JSON。

## 传统 vs AI 业务设计差异

| 维度 | 传统 DB 设计 | AI 业务 DB 设计 |
|------|------------|----------------|
| 数据来源 | 用户表单输入 | LLM 生成 + 用户输入 + 向量化 |
| 字段类型 | 标量为主 | 标量 + 向量 + jsonb |
| 查询方式 | SQL 精确查询 | SQL + 向量相似度 + JSON 查询 |
| Schema 偏定 | 字段固定，改表要迁移 | 部分字段灵活（jsonb 可动态扩展） |
| 索引策略 | B-Tree | B-Tree + HNSW（向量）+ GIN（jsonb） |

## 适用边界：jsonb vs 拆成关联表

不是所有嵌套结构都应该塞进 jsonb。判断标准：

| 情况 | 方案 | 原因 |
|------|------|------|
| LLM 生成的一次性结构（考题、诊断结果） | `jsonb` | 结构不固定，拆表收益小 |
| 需要独立查询/更新的子实体 | 拆成关联表 | jsonb 内部元素不能高效单独更新 |
| 简单的标签/列表 | `text[]` | 不需要 jsonb 的复杂性 |
| 需要跨记录聚合统计的实体 | 拆成关联表 | jsonb 的聚合查询性能不如关联表 JOIN |

## 一句话带走

简单字段存标量，向量存 pgvector，复杂嵌套结构存 JSONB + Zod 强类型映射。
