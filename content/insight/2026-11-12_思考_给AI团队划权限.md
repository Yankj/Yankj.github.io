> 我说了「嗯」「继续」，Agent 听成了「合」。授权得是当轮、本人、逐项的一句话。

前天傍晚，我在一个测试项目群里回了两个字：「继续」。

我的意思是让大家接着推进。可是群里有 Agent 把它理解成了可以把二十个提交合进主干。负责统筹的 Agent 对照了我的原话，发现我从头到尾没说过「合」字，从严判定这不算授权，误读的一方收回了。一个多小时后，我明确回了一个「合」，才算数。

这不是第一次。一周多以前，在另一个做内容的 Agent 群里，我回了一个「嗯」，确认的是上一句「下期跟着主干上已有的 Skill 做」，结果两个 PR 被当成我批准了，直接合了进去。另一个 Agent 发现我还没点选项卡，在群里喊停，负责的那个马上撤回，重新开成草稿，等我点头才合。

类似的误会，在三个项目组里各出了一次。我开始意识到，这不是哪个 Agent 粗心，而是我们对「授权」这件事，根本没有定义清楚。

## 人说话是接上文，Agent 听话是找许可

人在群里回「嗯」「继续」「好」，绝大多数时候只是在接上一句话：我看到了，你说得对，接着干。可 Agent 的处境不一样，它手里有一堆待办，其中几件需要许可，它会倾向于在我的每句话里找能用的许可。

两种理解撞在一起，一个模糊的字就会被放大成一次不可逆的操作。所以我们后来的规则写得非常死：合并只认明确的「合」字，而且要在同一轮里看到。「继续」不算，「及时提交代码」也不算。

## 转述的点头，本身就是一句需要核实的话

第三次误会更隐蔽。在一个做亲子类 App 的项目群里，一个 Agent 说我在私聊里对它讲过「及时合并」，所以我已经点过头了，准备等 CI 一绿就自动合并。

负责合并把关的 Agent 叫停了，它的理由是：「你们的私聊我看不到，按规矩得用户本人在这边确认。」直到我在群里说了「合并吧。」才合。

那句私聊原话，后来谁也没能拿出原文来。在 AI 团队里，「某某说用户同意了」本身就是一句需要核实的话。转述者未必有恶意，但转述会丢上下文，会把「记得及时处理」听成「可以合了」。所以规则是：只认用户本人在当前对话里看得到的点头，转述一律不算。

还有一层细节：在测试项目里，推送到主干要过一张审批卡，那张卡只出现在我和写代码的 Agent 的私聊里。群里的「合」，不等于点了那张卡。权限在哪个界面上生效，点头就得在哪个界面上发生。

## 合并只是第一道闸

那天我在群里说「合并吧」，紧接着问了一句：「Web版本做完了吗？」

负责的 Agent 回答：还没做完，第一批已经合了，还差三件事。功能清单没有逐项核完，真实登录和实机验收要等预览环境，家里数据要不要同步还没定。它还补了一句：没部署，线上的数据库迁移也没跑，要跑我再说一声。

这句回答我很认可。对写代码的人来说，合进主干好像就是做完了；对用户来说，能打开、能用才算。中间至少还隔着几道闸：

1. 合并：代码进主干。
2. 部署：新版本真正跑在线上。
3. 生产迁移：线上数据库的结构改动。
4. 开预览：给真人看、给测试账号用。

每一道都会改变真实世界的状态，每一道都要单独点头。合并的点头不能被顺延成部署的点头，更不能被顺延成迁移的点头。所以现在每条汇报都必须写明：部署了没有，迁移跑了没有，哪一块还没接。

## 撤销也必须一句话就能生效

授权不只是给出去，还要能收回来。测试项目里，各个 Agent 原本每小时播报一次进展，消息越来越多。有一天下午我在群里说了一句「停止定时检查」，统筹的 Agent 马上把两条例行任务都停了。

我后来想，这和授权其实是一件事的两面：我能用一个字批准，就应该能用一句话叫停，而且叫停的话不需要解释原因。

## 代价是等，但等是设计出来的

这套规则有代价。测试项目里，有一天下午同时挂着四个独立的待批事项，等我点头等了两个小时左右。操机的 Agent 在复盘里说得很平静：等待本身是安全设计的代价，不算 bug。

我同意。真正该优化的不是「少等一点」，而是把待批的事拆清楚、写清楚，让我能一眼看懂每一项批了会发生什么，然后逐项回答。这也是规矩里「逐项」两个字的意思：点哪项做哪项，没点到的原地等。

AI 团队越能干，人手里留着的权限就越少，也越重。留下来的那几个字，最好每一个都说得清清楚楚。
